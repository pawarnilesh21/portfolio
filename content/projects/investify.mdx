## The problem

I built Investify as a solo project to bring financial goals and risk-based allocation into one workflow. The aim is to help a visitor organize planning inputs and explore an allocation, rather than leave calculations spread across separate tools. The public application includes a planning interface and an Express/MongoDB backend.

A critical constraint is the difference between the public demo and the newer local implementation. The public backend snapshot contains mock stock and mutual-fund data. The newer local version includes provider-backed market research. I keep those versions distinct here: the live link is a public demo, not proof that every local improvement is deployed.

## Architecture and data flow

The React interface collects planning inputs and calls modular Express routes. MongoDB stores application data. The available public code uses JWT authentication and bcrypt password hashing. Its recommendation controller filters predefined market records against inputs such as budget.

The newer local implementation adds saved goals, watchlists, revision history and Indian-market lookups. Its middleware checks signed bearer tokens against revocable session records. That is different from the cookie-session wording in an earlier resume, so this case study does not merge the two authentication designs.

## Engineering decisions and limits

The local planning implementation uses transactions and conflict detection to preserve revision history. Provider integration adds caching, timeouts, request coalescing and stale-data labels. These mechanisms address concrete failure cases: simultaneous edits, slow external APIs and old prices.

Those are local-code capabilities. The public repository must be brought into alignment before a reader can verify the complete newer architecture from GitHub alone. The deployed landing page also contains marketing figures that I have not established with usage evidence; they are not portfolio results.

## Results and next steps

The application demonstrates a full-stack planning workflow and a deeper local iteration on data integrity. Historical local verification records include backend, calculation and browser checks, but their counts differ from the resume and are not presented as a current aggregate.

My next step is to align the public source, deployed version and documentation, then provide a read-only walkthrough and a reproducible latency measurement. Until then, this page makes the version boundary explicit.
